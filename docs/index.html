The sign is in the last byte

A mainframe extract is bytes, not a file format. Nothing inside it says where one field ends and the next begins, whether a number is negative, or where its decimal point belongs. All of that lives in a separate document — and when the two disagree, the load still succeeds and the numbers are still wrong.

Who has this problem

Anyone moving decades of mainframe data into a warehouse, a lake, or a new system — which right now is most large banks, insurers, utilities and government agencies in Europe.

What you are given

Two files and no schema

A flat file of fixed-length records in EBCDIC, and a COBOL copybook describing the layout. The file has no header, no delimiters and no types. The copybook is the only thing that makes it readable — and it was last edited by someone who has retired.

What people do

Write a loader in an afternoon

Slice each record at fixed offsets, strip anything that isn't a digit, cast to a number, load it. It runs. It produces a table. Row counts match the source exactly, which is the check most teams stop at.

What goes wrong

Nothing raises an error

Credits arrive as charges. Amounts arrive a hundred times too large. A code column silently falls through every branch. There is no exception, no rejected row, no red mark — just a column of plausible numbers that are wrong, sitting in a warehouse being reported on.

Three ways to read the same column

Not three settings. Three real loaders, of which two are common and both are wrong.

Correct

Recover the digit hiding under the sign, apply the sign, then shift the implied decimal point that the copybook declares and the file does not store.

# PIC S9(08)V99, EBCDIC, trailing overpunch
digits, sign = split_overpunch(text)
value = Decimal(digits) * sign
value = value.scaleb(-2)   # the V99

What overpunch does.

Sign ignored

The last byte of a negative value is } or J–R, not a digit. Strip non-digits and it disappears — along with the digit sharing that byte. Every credit silently becomes a charge.

value = int(re.sub(r"\D", "", text)) / 100

The most common mistake, because it looks defensive.

Digits only

The same, plus forgetting that V99 means two decimal places that are never written down. Cents are read as whole units and every figure is a hundred times too large.

value = int(re.sub(r"\D", "", text))

Usually spotted — but only when someone already knows the true total.

Vocabulary

  
Six terms that carry all the trouble.

  

    
Copybook
A fragment of COBOL declaring a record's fields in order.
      It is the schema, kept in a separate file from the data, with nothing enforcing that the two agree.

    
EBCDIC
IBM's character set, older than ASCII and incompatible with it.
      Several variants exist — cp037, cp500, cp1047 — differing on characters people actually use.

    
PIC S9(08)V99
Eight digits, then two more after an implied decimal
      point. S means signed. Ten bytes on disk, no point, no sign character.

    
Overpunch
The sign, encoded into the upper half of the last byte,
      leaving the digit in the lower half. A term inherited from punched cards, where it was an
      extra hole in the same column.

    
COMP-3
Packed decimal: two digits per byte, sign in the final
      nibble. Read as text it is unprintable garbage; read as a string it is silently truncated.

    
88-level
A named condition on a field's value. Two of them can
      claim the same value, which no tool can resolve — and one that guesses is worse than one that stops.
